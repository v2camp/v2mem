# 实验：工程记忆覆盖度对检索注入的影响

> **问题**：某个工程（`training-products`）的检索命中率长期为 0，是检索实现不行，还是该工程在库里
> 一条记忆都没有？灌入结论型记忆后，注入率能到多少、其中多少真的有用？
> **结论**：覆盖度是一阶约束（0% → 57%），但精度是二阶问题，且精度由**记忆写法**与**配额竞争**
> 决定，不由覆盖度决定。
> 复现脚本：[`scripts/exp-project-seed.sh`](../scripts/exp-project-seed.sh)（只读生产库，两臂都跑临时副本）。

---

## 1. 假设与设计

| 项 | 内容 |
|:---|:---|
| H1 | 该工程命中率为 0 的原因是**覆盖度**，不是检索实现缺陷 |
| H2 | 一旦有覆盖，注入率会升到 R2 阈值（30%）以上 |
| H3 | 记忆的**写法**（事实型 vs 现象→动作型）决定命中后是否有用 |
| 处理 | 给 T 臂灌 N 条该工程的结论型记忆；C 臂不动 |
| 对照 | 同一份库快照、同一批 query、同一个二进制、同样 `--limit 3 --max-chars 1200` |
| 唯一变量 | 库里有没有该工程的记忆 |
| 样本 | `read_traces` 中该工程、`gate_reason ≠ session_start` 的 49 条唯一 query（已冻结成 `queries.jsonl`，跨臂复用） |
| 指标 | ①注入率 ②注入字节 ③**人工相关性分级**（见 §4） |

为什么不用 `mem search` 而用 `mem hook`：用户看到的是注入结果，检索对了但被质量门/预算/去重挡掉，
`mem search` 看不见。两臂都走 `hook --event prompt-submit`，量的就是生产路径。

排除项：`gate_reason='session_start'` 的 12 条（开场类码表检索，不是用户提问，混进分母会稀释结论）。

**复现前提**：本实验已把 4 条种子写入生产库（§6），因此在当前库上重跑默认种子会因内容去重而
`ADDED=0`，脚本会显式报错拒绝——那不是失败，是「两臂已无差异」。要复现 C 臂的 0%，先按 §6 回退，
或在部署前的库快照上跑。

---

## 2. 三组配置

种子全部来自仓库内可核对的事实（课程工程 README、AGENTS.md 之外的历史决策），**刻意不导入规则类内容**
——规则本来就由宿主每轮注入，再进记忆库是重复占预算。

| 配置 | 条数 | 构成 | 注入率 | 平均字节 | 峰值字节 |
|:---|:---|:---|:---|:---|:---|
| **C（对照）** | 0 | 现库 | **0/49 = 0%** | 0 | 0 |
| **A** | 7 | 2 pitfall + 3 结构/构建 fact + 1 评测目录 fact + 2 decision | 31/49 = 63.3% | 394 | 698 |
| **B** | 5 | A 中把「构建 + workspace」合并成 1 条 | 28/49 = 57.1% | 365 | 727 |
| **C′（已部署）** | 4 | 2 pitfall + 2 decision，**剔除全部结构/构建类 fact** | 28/49 = 57.1% | 310 | 736 |

---

## 3. 配额竞争：结构类事实会把具体决策挤出去

A 配置下有一条可复现的现象：问「海量 schema 怎么注入」时，注进来的是「构建命令 / workspace 结构 /
评测目录」，而真正回答该问题的 `Text-to-SQL 检索链接` 决策**没进前三**。原因不是不支持，而是
泛化事实词汇面宽（`projects`、`pnpm`、`mvn`、`docs` 在长 prompt 里几乎必现），在 bm25 与结构支持上
稳定压过窄主题的决策条目，把 `--limit 3` 的槽位占满。

把它压成一条（B）、再彻底剔除（C′）后，同一批 query 的注入率只降 6 个百分点，但：

- `Text-to-SQL` 决策从 **0 次** 变为 **8 次**，其中在 schema 类 query 上命中；
- `图表两层契约` 从 0 次变为 3 次，在图表类 query 上命中。

也就是说，**删掉泛化事实不减少有效命中，只减少噪声**——它挤掉的是比它更该出现的内容。

---

## 4. 注入 ≠ 有用：人工相关性分级

对 C′ 臂 28 条注入逐条判定（判据：注入内容能否直接回答或实质缩小该 query 的搜索范围）。

| 级别 | 定义 | 条数 | 占全部 query |
|:---|:---|:---|:---|
| **A 直接有用** | 注入内容正是该 query 的答案或下一步动作 | 6 | 12.2% |
| **B 同域背景** | 同工程/同主题，但答不上这条 query 的具体问题 | 7 | 14.3% |
| **C 噪声** | 词面巧合，注入内容与 query 无关 | 15 | 30.6% |
| — 未注入 | — | 21 | 42.9% |

- 注入精度（A / 已注入）= 6/28 = **21.4%**；A+B 口径 = 46.4%。
- A 档 6 条中 4 条集中在 `.env` / api key 主题（「配置 key」「替换 key」「提示没配 key」「basic 支持 .env」），
  2 条命中两项架构决策（schema linking、图表两层契约）。
- 对照 A 配置（7 条种子、63.3% 注入率）：A 档只有 4 条（8.2%），精度 12.9%——**注入率更高，有用率更低**。

所以「命中率」不能单独当成功指标：它把「词面撞上」和「答上了」算成同一件事。

---

## 5. 结论

1. **H1 成立**。同一批 49 条 query，库里 0 条 → 0% 注入；4 条 → 57.1%。差异全部来自覆盖度，
   检索实现未变。
2. **H2 成立**，且远超 30% 阈值；但见第 4 节，57% 里有 3/4 不是直接有用的。
3. **H3 成立**。以「现象 → 原因/动作」组织的 pitfall，命中即有用（`.env` 四条全中）；
   以「路径/结构」组织的事实，是长 prompt 下最容易撞上的噪声源，还会挤掉具体决策。
4. **可迁移的写记忆规则**：能写进 AGENTS.md/CLAUDE.md 的结构与命令不要进记忆库（宿主已注入）；
   记忆库只收「跨会话才知道、且宿主不会自动注入」的结论，尤其踩坑与决策。
5. 因此「首次使用导入 Harness 项目记忆」应**只导历史结论**（复盘、决策、坑），不导规则正文与目录树；
   导入后必须过人工 accept，因为自动蒸馏产出的候选多是任务进展叙述（本案 7 条 pending 候选里
   4 条是「已完成并合入」式流水账，1 条引用的业务词 `车电吕` 已在现行课程文档中不存在）。

## 7. 局限（结论的边界）

1. **种子是按用户实际用词写的**，属于有偏构造：57% 是覆盖度收益的**上界**，不是期望值。
   无偏估计要看部署后的真实窗口（见 §8）。
2. **单工程、单 harness、n=49**，且 query 来自 10 天历史，工程本身也在变动
   （`车电吕` 那条候选已失效即为证据）。
3. **相关性分级是单人判定**，没有第二标注者，A/B 边界（如「替换 eval judge key」）存在主观性。
4. 相关性只判「是否答得上」，未判「答上了模型是否采纳」——后者需要 `adopted` 反馈或人工回看会话。

---

## 8. 后续

1. **真实窗口观测**：部署后按 12h 巡检看 `training-products` 的 R2。有偏上界 57%，若真实值落在
   15–30%，说明差距来自「用户用词与种子用词不一致」，下一步该做的是 query 归一化而不是继续加记忆。
2. **剪枝判据**：若连续两个窗口出现「注入率 >40% 但 `adopted/read` 无变化」，按 §5 结论 4 剪掉
   宽词汇条目。`92100495`（env.ts）覆盖了 27/49 条 query，是最可能的噪声源。
3. **导入通道**：本实验只用了 `mem add`。若要做 `mem import`，形态应是「写入 candidates
   （`source=import-proposal`）→ 人工 accept」，并复用本脚本做导入前的 A/B 预演。
4. 判据表暂无「注入精度」项。本实验给出的 21% 可作为将来定阈值的实测锚点，但**不要**据此
   现在就加判据——单工程单窗口不足以定阈值。
